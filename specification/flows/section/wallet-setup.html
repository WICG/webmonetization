Wallet setup

This section specifies how the user can set their [=wallet address=] for Web Monetization in the user agent.

Terms

Web Monetization page
Refers to the browser's UI for managing Web Monetization settings, accessible via a browser specific URI. In Chromium based browsers, the page can be located at `chrome://webmonetization`.
Web Monetization setup page
Refers to the browser's UI for setting up Web Monetization on the [=Web Monetization page=]. The UI lets user specify the [=wallet address=], and the budget. An example of such a UI could be an "Add a Wallet" button that opens a dialog for entering this information, with an "Add" button that starts the wallet connection process when clicked.
Interactive grant
Open Payments requires outgoing payment [=grants|grant=] requests to be interactive. When a grant request is interactive, it means explicit interaction by an individual (typically the client’s end user) is a required step in the delegation process.
After the grant request is made, the client must poll for a Grant Continuation request so the [=AS=] knows to issue an access token.
Redirect URI
The redirect URI is an URL the user is redirected to in order to accept or decline the outgoing payment grant ([=interactive grant=]) when conneting their [=wallet=] to the browser.

Connecting a wallet

The user can initiate the wallet setup from the [=setup page=].

The [=setup page=] UI allows the user to enter: (1) a [=wallet address=]; (2) a spending budget; and (3) a renewal monthly flag.

Only one wallet can be connected at a time, and a connected wallet is disconnected before a new wallet connection is started.

When the user starts a new wallet connection from the [=setup page=], the browser MUST run the following steps to start a wallet connection:

  1. If the result of the [=get user wallet=] algorithm is not null:
    1. Ask the user to explicitly confirm that the connected wallet will be disconnected. If the user does not confirm, return.
    2. Run the [=disconnect a wallet=] algorithm.

    Disconnecting first means the previous grant is cancelled with its authorization server and the previous connection's wallet, grant and keys are removed from {{Storage}}. A failed wallet setup therefore never leaves new state next to an old wallet and grant. The previous {{Storage/maxRateOfPay}} may be retained (see [=clear wallet data=]) until the new connection is stored.

  2. If the result of the [=get auth keys=] algorithm is null, run the [=generate an Ed25519 key pair=] algorithm.

    After the previous step no wallet is connected, so a key pair that still exists here was kept by an earlier wallet setup that failed before a grant was requested (see [=abort wallet setup=]). It is reused so that the user does not have to register a new public key with their wallet provider after, for example, mistyping their [=wallet address=].

  3. Display the [=encoded public key JWK=] (representing the [=Ed25519 public key=]) from the result of the [=get auth keys=] algorithm, so the user can copy or upload it to their wallet provider.
  4. When the user submits the [=setup page=] with a [=wallet address=] |walletAddress|, a budget |budget| and a renewal monthly flag |renewMonthly|, run the [=process the wallet setup=] algorithm with |walletAddress|, |budget| and |renewMonthly|.

To abort wallet setup, given an optional |continueUri:DOMString| and an optional |continueAccessToken:DOMString|:

  1. If |continueUri| and |continueAccessToken| are not null:
    1. Run the [=send a cancel grant request=] algorithm with |continueUri|, |continueAccessToken| and false.

      This revokes the pending grant with the authorization server so that the user cannot still approve it after the wallet setup has failed. If the grant is already gone, for example because the user declined it, the request fails. The failure is ignored and the user is not notified, because the wallet setup has already failed.

    2. Run the [=clear wallet data=] algorithm.
  2. Return failure.

If the wallet setup fails before a grant is requested, for example because the [=wallet address=] cannot be resolved, {{Storage}} is left unchanged. The key pair is kept and reused by the next [=start a wallet connection=], so the public key the user has already registered stays valid. Once a grant was requested, the key pair is removed together with any other state of the failed wallet setup, and the next wallet connection generates a new key pair that the user has to register with their wallet provider.

Because any previously connected wallet was disconnected before the wallet setup started, this only removes state created by the failed wallet setup.

To process the wallet setup, given a string |walletAddress:DOMString| (the [=wallet address=] provided by the user), a number |budget:number| (a spending budget requested from the wallet for outgoing payments, expressed in the wallet asset), and a boolean |renewMonthly:boolean| (whether the budget is renewed monthly by the wallet):

  1. If the result of the [=get auth keys=] algorithm is null, return the result of running [=abort wallet setup=].
  2. Let |walletAddressDetails:WalletAddressDetails| be the result of the [=send a wallet address request=] algorithm on |walletAddress|.
  3. If |walletAddressDetails| is failure, return the result of running [=abort wallet setup=].
  4. Let |interval:DOMString| be an ISO 8601 repeating interval if |renewMonthly| is `true`. The starting date for the repeating interval needs to be the user's current date (ISO String). 
              R/2025-01-28T02:12:16.254Z/P1M
  5. Let |pendingGrant:PendingGrant| ({{PendingGrant}}) be the result of the [=send an outgoing payment and quote grant request=] algorithm with |walletAddressDetails|, |budget| and |interval|.

    Since we ask for access to outgoing payments, the user will have to interact with the grant (approve or decline). Currently in Open Payments, only the grants that request access to outgoing payments are interactive.

  6. If |pendingGrant| is failure, return the result of running [=abort wallet setup=].
  7. Let |continueUri:DOMString| be |pendingGrant|'s {{PendingGrant/continue}}.{{Continue/uri}} property at which the client instance can make continuation requests.
  8. Let |continueAccessToken:DOMString| be |pendingGrant|'s {{PendingGrant/continue}}.{{Continue/access_token}}.{{ContinueAccessToken/value}} property.
  9. Let |redirectUrl:URL| be the result of [=URL parser|parsing=] |pendingGrant|'s {{PendingGrant/interact}}.{{PendingInteract/redirect}} property ([=Redirect URI=]).
  10. If |redirectUrl| is failure or |redirectUrl|'s [=url/scheme=] is not `https`, return the result of running [=abort wallet setup=] with |continueUri| and |continueAccessToken|.
  11. Run the [=create a fresh top-level traversable|creating a fresh top-level traversable=] algorithm given |redirectUrl|, to redirect the user to their wallet's [=IdP=], where the user can accept or decline the grant.

    Whether the [=traversable navigable=] is presented as a new tab, a new window or a popup-style window is [=implementation-defined=].

  12. Let |baseWait:number| be |pendingGrant|'s {{PendingGrant/continue}}.{{Continue/wait}} property if it exists, or 5 otherwise. If |baseWait| is less than 1, set |baseWait| to 1. Let |wait:number| be |baseWait|.

    5 seconds is the default polling interval defined by GNAP. The lower bound keeps the browser from sending continuation requests in a tight loop.

    We cannot use the {{PendingInteract/finish}} redirect method as browser's internal URLs can not be opened from an external source. In the Open Payments scenario, the [=AS=] will have to redirect the user to the internal browser page for Web Monetization to continue the flow.

    Since we cannot use Open Payments' redirect {{PendingInteract/finish}} method, we will have to check every |wait| seconds (polling) to retrieve information about the grant (whether user accepted or rejected the grant).

  13. Let |finalizedGrant:Grant?| be null.
  14. Let |retries:number| be 0.

  15. While |finalizedGrant| is null:

    1. Wait |wait| seconds.
    2. Let |result| be the result of running the [=send a continue grant request=] algorithm given |continueUri| and |continueAccessToken|.
    3. If |result| is `"retry"`:
      1. Increment |retries| by 1.
      2. If |retries| is greater than an [=implementation-defined=] limit, return the result of running [=abort wallet setup=] with |continueUri| and |continueAccessToken|.
      3. Increase |wait| by 5.
      4. [=iteration/Continue=].

      A network error, a server error or a GNAP `too_fast` error does not end the wallet setup, because the user may still be approving the grant. The browser backs off and tries again.

    4. If |result| is failure, return the result of running [=abort wallet setup=] with |continueUri| and |continueAccessToken|.

      This includes the user declining the grant.

    5. Set |retries| to 0.
    6. If |result| is a {{Grant}}, set |finalizedGrant| to |result|.
    7. Otherwise, if |result| is a {{Continue}}:
      1. Set |continueUri| to |result|'s {{Continue/uri}}.
      2. Set |continueAccessToken| to |result|'s {{Continue/access_token}}.{{ContinueAccessToken/value}}.
      3. If |result|'s {{Continue/wait}} exists, set |baseWait| to the greater of |result|'s {{Continue/wait}} and 1.
      4. Set |wait| to |baseWait|.

      Each continuation response replaces the previous continuation handle, including its URI. Any back-off from earlier retries is dropped, so polling continues at the interval requested by the authorization server, or the default interval if it did not request one.

    8. Otherwise, return the result of running [=abort wallet setup=] with |continueUri| and |continueAccessToken|.

    The algorithm does not continue until the grant is finalized or the wallet setup is aborted. Implementations run these steps without blocking the user interface.

  16. Let |assetScale:long| be |walletAddressDetails|'s {{WalletAddressDetails/assetScale}}.
  17. Let |maxRateOfPay:long long| be Math.round(|budget| * Math.pow(10, |assetScale|)).

    This converts the user-entered monthly budget in the wallet asset into a [=scaled amount=] integer. The resulting value is stored as {{Storage/maxRateOfPay}} and used to compute the payment amount and delay.

  18. Run the [=store wallet connection=] algorithm with |walletAddressDetails|, |finalizedGrant| and |maxRateOfPay| serialized as a string.

Disconnecting a wallet

The user can disconnect their previously connected [=wallet=] via the [=setup page=] using a UI control (e.g. a "Disconnect Wallet" button) that requires explicit user confirmation (such as a confirmation dialog).

Disconnecting a wallet revokes the active grant (if any) and clears state from {{Storage}}.

To disconnect a wallet:

  1. Let |storage:Storage| be the result of the [=get storage=] algorithm.
  2. If |storage|'s {{Storage/grant}} is not null, then:
    1. Let |grant:Grant| be |storage|'s {{Storage/grant}}.
    2. Let |continueUri:DOMString| be |grant|'s {{Grant/continue}}.{{Continue/uri}}.
    3. Let |continueAccessToken:DOMString| be |grant|'s {{Grant/continue}}.{{Continue/access_token}}.{{ContinueAccessToken/value}}.
    4. Run the [=send a cancel grant request=] algorithm with |continueUri| and |continueAccessToken|.

      Failure to cancel (e.g. network error) SHOULD surface a non-blocking warning to the user; the browser MAY still proceed with local cleanup.

  3. Run the [=clear wallet data=] algorithm.

    All grant data, authentication keys, and wallet details are removed. Reconnecting will generate a new key pair requiring re-registration of the public key.
